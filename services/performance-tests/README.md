# performance-tests

## Role in CatFi

Isolated Gatling HTTP load tests for the browser-facing BFF. No load is generated by `mvn verify`.

## Source-level capacity review

See [performance audit](../../docs/PERFORMANCE_AUDIT.md). Each virtual user
makes **three** BFF requests (CSRF + login + business), so 100/1000/5000
session arrivals/s imply up to 300/3000/15000 HTTP requests/s, not proven
business throughput. No actual 100/1000/5000 RPS benchmark has been run in
this patch. BCrypt and per-login database/audit work dominate this scenario.
Separate realistic session-reuse and write-pipeline benchmarks remain necessary.

## Workload and safety

`rps` is the **arrival rate of virtual-user sessions**, not a guaranteed count of
business endpoint calls/sec. Every virtual user obtains a session CSRF token,
logs in with a demo-agent account, and then issues one dashboard read or an
opt-in disaster write. Login and CSRF calls also count toward BFF HTTP traffic.

The default workload is **100% read-only** to avoid creating thousands of disaster
and financial events. Set both `-DwritePercent=5 -DallowWrites=true` only against
a disposable environment. Do not use a production system or real customer data.
The plan rejects NaN, non-positive rates, invalid durations and implicit writes.

Set agent credentials outside source control (PowerShell example):

```powershell
$env:CATFI_LOAD_AGENT_USER = 'demo.agent'
$env:CATFI_LOAD_AGENT_PASSWORD = $env:CATFI_DEMO_AGENT_PASSWORD
if (-not $env:CATFI_LOAD_AGENT_PASSWORD) { throw 'Set CATFI_DEMO_AGENT_PASSWORD first' }
.\mvnw.cmd -pl services/performance-tests gatling:test '-Drps=100' '-DdurationSeconds=120'
.\mvnw.cmd -pl services/performance-tests gatling:test '-Drps=1000' '-DdurationSeconds=120'
.\mvnw.cmd -pl services/performance-tests gatling:test '-Drps=5000' '-DdurationSeconds=120'
```

For a separately provisioned **test-only** Kafka pipeline, append
`'-DwritePercent=5' '-DallowWrites=true'`. Reports: `services/performance-tests/target/gatling/`.
Global error rate must be under 1%; **dashboard** response p95 under 500 ms and
p99 under 1000 ms. The dashboard thresholds exclude login/CSRF requests; report
both business and auth metrics. Compare throughput, percentiles and errors
with Prometheus/Grafana metrics, database connections, CPU and Kafka consumer lag.

**Do not interpret 5000 RPS as a capacity promise**: a shared laptop and a BFF
performing BCrypt per request can become the bottleneck. For meaningful results
use an isolated load generator, controlled data, a stable warm-up and realistic
session reuse. The current scenario intentionally measures authentication overhead.

Run configuration unit tests: `./mvnw -pl services/performance-tests test`.
